## 1. Project & Domain Context

**MDIP** is a schedule delay-risk and Critical Path Method (CPM) intelligence platform built for **project-based / Engineer-to-Order (ETO) / Make-to-Order (MTO) custom manufacturing** (reference manufacturing scope: tooling, CAD/CAM engineering, alloy procurement, CNC machining, stamping/forming, subcontract heat treatment/coating, precision assembly, CMM quality inspection, and dispatch).

### Why We Need Real Datasets Right Now
Today, MDIP's ML models are trained exclusively on **synthetic data** generated by heuristics in `backend/ml/generate_dataset.py`:
- **Current training set (`backend/ml/data/synthetic_wbs_tasks.csv`):** `7,855` tasks across `900` synthetic manufacturing project DAGs (`late_rate = 0.4644`).
- **Real historical tasks (`backend/ml/data/historical_wbs_tasks.csv`):** `0` rows (`n_real_tasks = 0` in `backend/ml/artifacts/model_card.json`).
- **Current synthetic held-out metrics (`model_card.json`):**
  - Classifier `roc_auc`: `0.9297` (vs `baseline_rule_roc_auc`: `0.7135`)
  - Classifier `f1`: `0.8373` (`precision`: `0.8126`, `recall`: `0.8635`, `accuracy`: `0.8457`, `brier`: `0.1062`)
  - Hurdle regressor `slip_mae_days`: `0.914` days (`conditional_slip_mae_days`: `0.921` days)

Because synthetic labels follow the simulator's formulas, high synthetic ROC-AUC does **not** prove generalization to real factory/project execution noise. We need **real empirical planned-vs-actual activity schedules or ERP manufacturing work-order routing logs** to evaluate out-of-sample on real projects (`real_validation_metrics`) and retrain the model (historical rows receive `HISTORICAL_SAMPLE_WEIGHT = 5.0` vs `1.0` for synthetic rows).

## 2. How MDIP's ML Pipeline Works (Exact Technical Spec)

Any candidate dataset must fit (or be ETL-convertible into) this pipeline:

### A. CPM Graph Pass (`backend/schedule_parser.py` -> `compute_cpm`)
1. Reads `.csv`, `.txt`, `.xlsx`, `.xlsm`, or `.xls` (max upload size on HTTP API: `5 MB`, though local CSV training has no HTTP limit).
2. Normalizes rows (`planned_days >= 1.0`, optional `actual_days`, `predecessors` DAG edges).
3. If no dependency column exists, treats tasks in a project sequentially (`T[i-1] -> T[i]`).
4. Runs forward/backward CPM passes in topological order (`_topo_order` / Kahn's algorithm) to derive:
   - `start_day` (Early Start in days)
   - `float_days = int(round(max(0.0, LateFinish - EarlyFinish)))`
   - `critical = (float_days == 0)`
   - `upstream_slip_days`: max cumulative slip carried forward from upstream predecessors (`max(0.0, upstream + (actual_days - planned_days))`)
   - `variance_days = actual_days - planned_days`

### B. Exact 18 Input Features (`backend/ml/features.py` -> `FEATURE_NAMES`)
Both training (`backend/ml/train.py`) and live inference (`backend/ml/predictor.py`) compute identical features via `task_features()`:

#### Numeric Features (9)
| Feature Name | Type | Derivation & Exact Meaning | Default if Missing in Raw Data |
|---|---|---|---|
| `planned_days` | `float` | Planned/baseline activity duration (`>= 1.0` days). | **Required** (cannot be missing) |
| `float_days` | `float` | CPM total float `(LS - ES)` computed from DAG (`0` on critical path). | Computed by `compute_cpm` |
| `on_critical_path` | `0.0 / 1.0` | `1.0` if `float_days == 0` (critical path), else `0.0`. | Computed by `compute_cpm` |
| `forecast_variance_days` | `float` | `actual_days - planned_days` during live mid-project scoring. **Anti-leakage rule:** set to `0.0` during `ingest_historical_schedule` so a task's outcome never leaks into its own features. | `0.0` in historical training |
| `upstream_slip_days` | `float` | Max realized/propagated overrun carried from predecessor tasks before this task starts. | Computed by `compute_cpm` |
| `external_dependency` | `0.0 / 1.0` | `1.0` if step depends on external supplier/subcontractor. | Auto-`1.0` if category is `procurement` or `subcontract` |
| `n_predecessors` | `float` | Count of direct predecessor tasks (`len(predecessors)`). | `0` or `1` (sequential fallback) |
| `resource_utilization` | `float` | Work-center capacity load (`0.0–1.05`; percentage strings like `88%` auto-divide by `100`). | Category default (`0.60–0.90`, see `DEFAULT_UTILIZATION`) |
| `drawing_revisions` | `float` | Number of engineering drawing/spec revisions (ECNs) on the task. | `0.0` |

#### One-Hot Work Center Category Features (9)
`wc_subcontract`, `wc_procurement`, `wc_engineering`, `wc_stamping`, `wc_machining`, `wc_assembly`, `wc_quality`, `wc_logistics`, `wc_other`.

`infer_category(task_name, work_center)` matches keywords in exact priority order:
1. `subcontract`: `subcontract`, `heat treat`, `hardening`, `coating`, `plating`, `outsourc`, `furnace` (default util `0.75`)
2. `procurement`: `procure`, `raw material`, `raw ingot`, `ingot`, `material`, `purchase`, `supply chain`, `receiving`, `vendor` (default util `0.70`)
3. `engineering`: `drawing`, `cad`, `cam`, `design`, `blueprint`, `sign-off`, `engineering review` (default util `0.85`)
4. `stamping`: `stamp`, `press`, `forming`, `die` (default util `0.90`)
5. `machining`: `cnc`, `milling`, `lathe`, `machin`, `edm`, `grind`, `turning` (default util `0.88`)
6. `assembly`: `assembl`, `cleanroom`, `fitting` (default util `0.85`)
7. `quality`: `cmm`, `metrology`, `quality`, `inspection`, `qa `, `acceptance test` (default util `0.75`)
8. `logistics`: `logistic`, `dispatch`, `packag`, `shipping`, `dock` (default util `0.60`)
9. `other`: fallback (default util `0.80`)

### C. Prediction Targets (`backend/ml/train.py`)
1. **Binary classification (`XGBClassifier`):**
   ```text
   realized_slip_days = max(0.0, actual_days - planned_days)
   late = int(realized_slip_days > float_days + 0.5)
   ```
   *(Predicts whether a task finishes later than its CPM float buffer `+ 0.5` day tolerance, i.e., delays downstream/project.)*
2. **Conditional regression (`XGBRegressor`):**
   - Trained only on rows where `late == 1` (`objective="reg:squarederror"`, clipped to `[0.5, 20.0]` days at inference).
   - Expected unconditional slip: `E[slip] = P(late) * E[slip | late == 1]`.
3. **Train/Test Split Rule (`GroupShuffleSplit`):**
   - Split strictly by `project_id` (`test_size=0.2`, `SEED=42`), **never** random row-level split, so tasks from the same project cannot leak between train and test sets.
   - If `n_real_projects == 1`: trains on synthetic, validates out-of-sample on the 1 real project (`evaluation_mode = "out_of_sample_single_project"`), then blends for production weights.
   - If `n_real_projects >= 2`: holds out `20%` of real projects (`evaluation_mode = "held_out_real_projects"`) and reports separate `real_validation_metrics` alongside `synthetic_test_metrics`.

## 4. What Datasets to Search For (Inclusion & Exclusion Criteria)

### Tier 1 — Highest Value (Direct Multi-Project WBS / Job-Shop Schedules)
Look for datasets containing **multiple completed projects or manufacturing orders (`>= 10` projects, ideally `50–500+` projects / thousands of tasks)** with:
1. **Task-level / Operation-level rows** grouped by `project_id` / `order_id` / `case_id`
2. **Both Baseline/Planned AND Actual** duration OR `(Planned Start, Planned End, Actual Start, Actual End)` timestamps
3. **Precedence / DAG dependencies** (`predecessors` / `successors`) OR sequential routing steps (`operation_seq`)
4. **Resource / Work Center / Machine / Activity Name** labels

**Specific high-probability open dataset ecosystems & benchmarks to search:**
- **OR-AS / UGent Empirical Project Database (Batselier & Vanhoucke)** — real-life empirical project schedules with baseline schedules, actual execution tracking periods, network topologies, and Earned Value Management (EVM) data (`projectmanagement.ugent.be` / Mendeley / Kaggle mirrors).
- **4TU.ResearchData / Zenodo / IEEE DataPort — Manufacturing Production Process Event Logs (Process Mining / BPI / ERP SAP PP logs):** real factory production orders containing `Order ID` (`project_id`), `Work Center` (`machining`, `turning`, `heat treat`, `quality`, `packing`), `Planned Start/Finish`, and `Actual Start/Finish`.
- **Kaggle / Mendeley Data / Figshare / Harvard Dataverse / GitHub:**
  - CNC / Metal Fabrication / Tool & Die / Stamping / Automotive / Aerospace ETO manufacturing work-order schedules
  - Industrial EPC / Engineering / Construction / Turnaround / Maintenance (Shutdown/Turnaround WBS) schedules exported from Primavera P6 (`.xer`, `.csv`) or MS Project (`.mpp`, `.xml`, `.csv`) that include both Baseline and Actual dates + Predecessors
  - Open government infrastructure / public works / defense / R&D activity-level project tracking datasets that include WBS Baseline vs. Actual durations + predecessor IDs.

### Tier 2 — Useful With Light Python ETL Transformation
Acceptable if we can cleanly derive the required columns via a short Python normalization script before calling `ingest_historical_schedule`:
- **Timestamps instead of durations:** `planned_days = (planned_end - planned_start)`, `actual_days = (actual_end - actual_start)` (can be fractional days or hours converted to 8h/24h days, clamped `>= 1.0` or scaled consistently across the project).
- **Sub-day shop-floor hours/minutes:** If a real CNC/assembly job-shop log measures operations in **hours** (e.g., `2h` to `80h`), explicitly note the unit so we decide whether to map `hours -> shift days (hours / 8.0)` or retain real manufacturing task units.
- **No explicit dependency column:** Acceptable **if** operations have a strict sequential `operation_number` / `routing_step` per `order_id` (MDIP automatically chains sequential tasks when no dependency column is present).

### Hard Exclusions (Do NOT Return These)
1. **Pure sensor / predictive maintenance time-series only** (e.g., NASA C-MAPSS turbofan RUL, AI4I 2020 vibration/torque classification, bearing fault audio) — these have no planned vs. actual schedule durations or task DAGs.
2. **Project-level summary tables without task/activity breakdown** (1 row = 1 whole project, e.g., only total project cost/duration overrun with no WBS tasks).
3. **Simulated / synthetic / benchmark-only scheduling instances without empirical execution actuals** (e.g., standard PSPLIB J30/J60/J120 files only contain nominal deterministic durations and resource limits, **not** real realized actual delays).
4. **In-progress / static plans with no realized actual outcomes** (only planned duration, missing actual finish/duration).
5. **Paywalled, broken-link, or request-only private datasets** (must have a verifiable public download URL or repo path and clear open license).
